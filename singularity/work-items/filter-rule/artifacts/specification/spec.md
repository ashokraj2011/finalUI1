# Specification — filter-rule

## Agent brief

The rule authoring experience needs a dedicated filter block that runs before rule evaluation. The user must be able to choose searchable attributes, apply comparison and range operators, and sort results before the engine consumes them. This specification defines the UI behavior, required permissions, empty and failure states, and the acceptance criteria for the filter configuration and result ordering.

## Actors

- Visual designer: creates and edits rules in the authoring page and configures filter criteria.
- Rule engine: evaluates the final rule set after filtering has reduced the candidate records.
- Reader or reviewer: opens the rule design to inspect configured filter logic without modifying it.

## User scenarios

### S1 — Configure a filter before rule evaluation

**Priority:** P1
**Actor:** Visual designer
**Context:** The designer is editing a rule and needs to limit which records are considered before the rule engine evaluates conditions.

- **Given** the designer opens the rule authoring page with a rule that supports filtering
  **When** they add a filter condition, choose an attribute, operator, and value, and save the rule
  **Then** the filter is persisted with the rule and applied before rule evaluation

- **Given** the designer chooses a field that exists in the rule model
  **When** they compare numeric or date values using supported operators
  **Then** only matching records advance to rule evaluation and the invalid field/operator combinations are blocked

### S2 — Order filtered results before evaluation

**Priority:** P1
**Actor:** Visual designer
**Context:** The designer needs the filtered candidate set to be ordered consistently before the engine evaluates rules.

- **Given** multiple records match the filter criteria
  **When** the designer selects a sort attribute and direction
  **Then** the filtered set is ordered deterministically before further rule processing

- **Given** the designer selects a range or first/last slice in the filter block
  **When** the range is applied
  **Then** only the selected subset is considered for evaluation and the selection is visible in the UI

### S3 — Handle empty or failed filter states

**Priority:** P2
**Actor:** Visual designer
**Context:** The designer opens or saves a filter that has no matching data or an unavailable dependency.

- **Given** no records match the current filter definition
  **When** the rule is saved or previewed
  **Then** the UI shows an empty result state and exposes the reason without crashing

- **Given** an attribute, data source, or value cannot be resolved
  **When** the filter is evaluated
  **Then** the UI shows the failure state and prevents incomplete filter configuration from being accepted

## Failure and empty states

- **Empty:** If no items match the filter, the filter result displays an empty state with a clear message and no rule evaluation is executed against an empty candidate set.
- **Failure:** If a filter field or data source is missing, invalid, or unavailable, the UI prevents save and highlights the invalid rule instead of silently losing the filter.
- **Partial:** If only some fields are configured, the rule is treated as incomplete until the required values are present; incomplete filters are not persisted as valid rules.

## Permissions

- Visual designer may add, edit, remove, and save filter criteria for a rule they own.
- Reader or reviewer may inspect the configured filter and its order, but may not modify filter logic without design authority.
- Rule engine may only consume the filtered and ordered candidate set produced by the authoring layer; it does not change the filter configuration itself.

## Boundary conditions

- The filter block operates before rule evaluation and does not alter the underlying rule semantics.
- The system must support a predefined set of rule attributes drawn from the existing rule model and must reject unknown fields.
- Supported operators include equality, comparison, range, and grouping semantics for the filter logic.
- Sorting is limited to one active sort attribute with ascending or descending direction in the initial implementation.
- The filter range selection may specify a subset using first/last or index-based range semantics as defined by the rule authoring UI.
- All invalid or partial filter states must be surfaced in the UI before the rule is considered valid for save.

## Requirements

1. The rule editing experience shall include a dedicated filter block that is evaluated before rule execution, and this block shall be represented in the authored rule model. [filter-rule:REQ-001]
2. The filter block shall allow the designer to select a supported attribute, an operator, and a value for at least the supported rule-model fields defined by the current schema. [filter-rule:REQ-002]
3. The filter block shall support comparison and range-based operators, and it shall reject unsupported combinations before the rule is saved. [filter-rule:REQ-003]
4. The filtered result set shall respect the configured sort order and shall present a deterministic ordering before the rule engine evaluates the final rule. [filter-rule:REQ-004]
5. The filter block shall allow the designer to apply a first/last or range-based subset selection before evaluation without altering the original rule definition. [filter-rule:REQ-005]
6. The rule authoring UI shall show an explicit empty state when no records match the current filter and an explicit failure state when the filter cannot be evaluated. [filter-rule:REQ-006]
7. The system shall prevent saving incomplete or invalid filter configurations and shall require the designer to resolve the error before proceeding. [filter-rule:REQ-007]
8. A reader or reviewer shall be able to inspect the configured filter and ordering without being able to mutate it unless they possess design authority. [filter-rule:REQ-008]

## Acceptance criteria

- The designer can add a filter condition to a rule and save it so that the candidate record set is narrowed before evaluation. [filter-rule:AC-001]
- The UI blocks unsupported field/operator combinations and shows validation feedback instead of accepting an invalid filter. [filter-rule:AC-002]
- When multiple records match, the sorted subset is displayed in the chosen order before the rule engine runs. [filter-rule:AC-003]
- If the filter yields no records, the user sees the empty state and no rule evaluation is attempted on the empty candidate set. [filter-rule:AC-004]
- If a dependency is unavailable or a field is invalid, the user sees the failure state and the rule cannot be saved until the issue is corrected. [filter-rule:AC-005]

## Non-functional requirements

- The filter configuration and validation feedback shall complete without blocking the authoring interaction beyond the time needed to render the current rule state. [filter-rule:NFR-001]
- The UI shall remain readable and operable for authors using standard accessibility controls and keyboard navigation when defining or validating filters. [filter-rule:NFR-002]
- Filter state and validation messages shall be clear enough that a reviewer can understand the logic without reverse engineering the underlying rule engine. [filter-rule:NFR-003]

## Assumptions

- The existing rule model already defines the supported set of fields available in the authoring UI.
- The rule engine continues to consume a filtered subset as its input and does not require a redesign of evaluation semantics for this story.
- The initial implementation targets a single sort attribute and deterministic ordering rather than multi-column sorting.

## Out of scope

- Replacing the rule engine evaluation model.
- Introducing multi-tenant or cross-repository filter policy changes.
- Reworking audit, security, or retention requirements outside the filter authoring flow.
